# Телефоны покупателей: E.164

`normalizePhone` в `src/lib/phone.ts` — единственная реализация нормализации.
Она принимает `+992900123456`, `992900123456`, `900123456`, пробелы,
скобки и дефисы, возвращая **`+992900123456`**. Национальная часть содержит
ровно 9 цифр и может начинаться с нуля: `+992005042828`, `992005042828`
и `005042828` возвращают **`+992005042828`**. Правила одинаковы для покупателя
и получателя. Неверная длина, чужой код страны, буквы, посторонние символы,
повторный или расположенный не в начале `+` и девять одинаковых цифр-заглушек
(включая `000000000`) возвращают `null`.
Международные номера других стран пока не поддерживаются.

## Реальная схема и миграции

Повторно проверены ограничения подключённой PostgreSQL:

- `users_phone_e164_check`: `CHECK (phone ~ '^\+[1-9][0-9]{7,14}$')`;
- `users_phone_key`: `UNIQUE (phone)`.

Плюс обязателен. Предыдущая рекомендация хранить номер без плюса была ошибочной.
Незакоммиченная `20260912_users_canonical_phone.sql` удалена. **Новая миграция
не нужна**, существующие ограничения не изменялись, миграции не выполнялись.
Существующие пользователи не переписываются и не удаляются, в том числе при
повторном оформлении сохраняется их прежнее имя.

Колонки email в `users` нет, форма его не собирает, фиктивная строка удалена.
Предыдущий аудит: 7 пользователей, дублей корректных номеров не обнаружено,
3 номера не проходят прикладную валидацию. Данные не исправлялись автоматически.

## Использование

- `src/app/checkout/page.tsx`: валидация и отправка канонического номера.
- `src/app/api/orders/route.ts`: переэкспорт общего обработчика из
  `src/app/api/admin/orders/route.ts`.
- `src/lib/customers.ts`: создание только с плюсом, поиск существующих по той же
  нормализации, включая прежнее форматирование. Id выбирается стабильно по
  created_at, id. Роли admin/super_admin исключены; номер только администратора
  даёт 409 при оформлении, не изменяя аккаунт.
- `src/lib/customer-scope.ts`, `src/app/admin/customers/page.tsx`: группировка
  покупателей по E.164, покупки и оплаты всех связанных id, правильная дата
  последнего заказа; отменённые заказы исключены из этих показателей.
- `src/app/admin/page.tsx`: поиск заказов по той же нормализации.

Оба маршрута оформления используют advisory lock по каноническому телефону
в READ COMMITTED транзакции. Отдельный писатель может не брать блокировку,
поэтому `INSERT users` дополнительно защищён SAVEPOINT. При PostgreSQL
`23505` именно от `users_phone_key` выполняются ROLLBACK TO SAVEPOINT и повторный
поиск пользователя. Транзакция заказа остаётся рабочей. Другие ошибки не
маскируются. UNIQUE гарантирует отсутствие одинаковых канонических строк.

Поиск прежнего форматирования читает телефоны пользователей и вызывает общую
TypeScript-функцию. Физического объединения строк нет. Для большой базы этот
проход по всем пользователям может потребовать оптимизации.

## Авторизация

В текущем репозитории `src/app/admin/login/page.tsx` и
`src/app/api/admin/login/route.ts` принимают **только пароль**, а
`src/lib/admin-auth.ts` проверяет cookie. Поля телефона и поиска администратора
по телефону в этом потоке нет. Эти файлы не менялись; вход по телефону нельзя
считать проверенным в отсутствующем потоке. Действующий вход по паролю и cookie
покрыт тестом. При подключении отдельного входа по телефону ему нужна та же
`normalizePhone` с результатом E.164, без изменения проверки пароля/ролей.

## Проверки

`node --test scripts/test-customer-phone.mjs` — 5 тестов:

- нормализация в `+992XXXXXXXXX`, неверные значения и идемпотентность;
- действующий вход администратора по паролю и cookie;
- два заказа с разным вводом используют один id, имя пользователя не меняется;
- вставка с настоящими CHECK/UNIQUE, скопированными из public.users во временную
  таблицу; номер без плюса отклоняется существующим E.164 CHECK;
- настоящая ошибка UNIQUE и восстановление транзакции через SAVEPOINT;
- старые варианты, объединение карточек, суммы оплат, отменённые заказы,
  последний заказ и SQL страницы с разным вводом поиска;
- два соединения с настоящей advisory lock и имитируемым хранилищем.

Тесты используют только временные таблицы с откатом; сценарий UNIQUE моделирует
появление конкурирующей записи между первым чтением и SAVEPOINT. Полный HTTP-заказ
в рабочую БД не создаётся, склад, доставка и резервы не меняются.
Дополнительно выполняются `npm run lint`, `npm run build`, `git diff --check`.
