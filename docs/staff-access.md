# Персональный доступ сотрудников Lotus

## Порядок обновления существующего магазина

Миграция **не запускается приложением**. Сначала подготовьте доступ, сохраняя работающую старую версию приложения. Не переключайте магазин на новый код до шага 4.

1. Сделайте обычную резервную копию БД. В pgAdmin подключитесь к базе магазина **владельцем таблиц**, откройте `src/db/migrations/20260916_staff_access.sql` и выполните целиком. Повторный запуск допустим. Если прикладная роль отличается от `lotus_app`, в том же соединении предварительно выполните `SET lotus.app_role = 'имя_прикладной_роли';`. Пароль роли не нужен в SQL. Существующие пользователи, роли, заказы и доставки сохраняются.
2. В терминале в корне проекта выполните `npm run staff:password -- "+992XXXXXXXXX"`, подставив телефон **существующего активного пользователя с ролью `super_admin`**. Команда использует локальные настройки подключения Next.js. Введите личный пароль длиной 12–128 символов дважды. Ввод скрыт; пароль не передаётся в аргументах, не выводится и не сохраняется открытым текстом. Скрипт проверяет роль повторно под блокировкой, проверяет полученный хеш и отзывает старые персональные сессии. Он не создаёт пользователей и не выдаёт роль сам.
3. Дождитесь сообщения `Personal password set and verified`. Если скрипт завершился ошибкой, **оставьте старую версию работающей**, исправьте миграцию/права/телефон и повторите шаг 2. Пользователя и его роль можно проверить read-only запросом: `SELECT u.name, u.phone, u.status FROM public.users u JOIN public.user_roles ur ON ur.user_id=u.id JOIN public.roles r ON r.id=ur.role_id WHERE r.code='super_admin';`. Не публикуйте результат.
4. Запустите новую сборку на локальном/закрытом адресе проверки и войдите на `/admin/login` с телефоном и личным паролем. Проверьте `/admin/staff`, выход и повторный вход. Затем переключите рабочий адрес на новую сборку и остановите старый процесс. **В новой версии общий вход и статический токен уже не принимаются**; обратного обходного пути нет. Не оставляйте старый процесс доступным извне.
5. После успешного личного входа удалите `ADMIN_PASSWORD` и `ADMIN_SESSION_TOKEN` из конфигурации развёртывания и перезапустите приложение. Старые cookie не дают доступ. `.env.local` в рамках разработки не изменялся.
6. Создайте сотрудников в `/admin/staff`. Выдавайте каждому свой временный пароль по личному каналу. После первого входа обязательна смена пароля, затем повторный вход. Для старых доставок выберите персонального курьера в разделе «Доставка»: текстовое имя само по себе не даёт сотруднику доступ. Автоматического сопоставления по имени и очистки исторических данных нет.

Для восстановления личного доступа владельца повторите шаг 2. Если в базе нет активного `super_admin`, владелец БД должен сначала проверить и назначить эту роль нужному существующему пользователю отдельно; скрипт намеренно не повышает права.

## Разрешения и хранение

Несколько ролей объединяют разрешения. `super_admin` получает все разделы; `florist` — заказы до «Готов», оплату, букеты, контакты покупателей заказов и доступные остатки без себестоимости; `inventory_manager` — склад, обе цены, поставщиков, поступления и модели; `courier` — только свои доставки и два последовательных перехода. Существующая роль `admin` сохраняется для истории, но не даёт новый доступ: назначьте нужную персональную роль. Страницы запрещают прямые URL через 404, API возвращают 401/403, чужая доставка — 404. Временный пароль ограничивает доступ страницей смены пароля.

Пароли: `crypto.scrypt`, случайная соль 16 байт, N=131072/r=8/p=1, сравнение `timingSafeEqual` ([документация Node.js](https://nodejs.org/api/crypto.html#cryptoscryptpassword-salt-keylen-options-callback)). Сессия: случайные 32 байта, в БД SHA-256 токена, срок 12 часов, cookie `httpOnly`, `SameSite=Lax`, `Secure` в production. Production должен обслуживаться через HTTPS. Проверки активности, ролей и срока выполняются по БД на запрос. Сброс пароля, изменение ролей, отключение и явный отзыв удаляют сессии.

Лимиты входа общие для процессов: 5 неудачных попыток на нормализованный телефон (или ограниченный хеш некорректного ввода) за 15 минут, 200 неудачных попыток суммарно за 15 минут; успешный вход сбрасывает лимит телефона. Ошибка не раскрывает наличие пользователя. На очень загруженной установке параметры лимитов нужно согласовать с реальной нагрузкой.

Важные изменения записываются в `admin_audit_log` в транзакции изменения. Приложение не получает UPDATE/DELETE журнала. Пароли, хеши паролей, cookie и токены в журнал не передаются. Закупочные цены сохраняются десятичными строками в `numeric`; обычное изменение цен не пишет складские движения. Средневзвешенная цена поступления рассчитывается PostgreSQL в `numeric`.

## Проверка в браузере после миграции

- Под каждой ролью проверить меню, прямой чужой URL и запрещённый HTTP-запрос. У курьера должны быть только его доставки, без самовывоза; запрос к чужой доставке — 404.
- Создать сотрудника, сменить временный пароль, изменить роли, сбросить пароль, отключить доступ и проверить ранее открытый сеанс. Попытаться отключить последнего супер-администратора.
- Проверить самовывоз «Готов → Выполнен» и доставку «Готов → Доставляется → Выполнен». Назначить курьера; пройти «Назначена → В пути → Доставлена» под ним.
- Сохранить `12,34` и `25.50` в ценах; отрицательное значение должно отклоняться. Проверить цены после обновления склада/конструктора, неизменный остаток и отсутствие нового движения; проверить проведение поступления.
- Добавить 10 одинаковых цветов, раскрыть группу, выбрать номер, изменить и удалить экземпляр. Проверить обе автокомпозиции, undo/redo, сохранение и повторное открытие корзины на узком экране.

Автоматические тесты БД создают только временные таблицы своего соединения. Миграция проверяется на этих таблицах, не на рабочих данных. Браузерные фикстуры блокируют запросы записи; тестовые GLB и профили Chrome удаляются.
